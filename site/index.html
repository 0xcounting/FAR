FAR — Free Asset Resolver

An open cross-reference between CAIP-19, CoinGecko IDs and ISO 24165 DTIs. Every lookup is a static file: no key, no rate limit, no server that can be down differently from any other file.

Try it

Type an asset name, ticker, CoinGecko ID, CAIP-19 or DTI. The resolver tries each route in turn and shows you which one answered — the same thing your code would do.

Lookups are case-insensitive — except one. Names, symbols, CoinGecko ids and DTI codes are all normalised, so USDC, usdc and UsDc are the same query. A CAIP-19 is not case-folded, and must not be: Move type tags (0x2::sui::SUI), Antelope symbol codes and base58 references are case-sensitive by their own specifications, so lowercasing one would name a different asset or nothing at all.

Note also that a ticker is not a CoinGecko id. usdc is a ticker; the id is usd-coin. That is why /cg/usdc.json returns 404 while /symbol/usdc.json returns 62 assets.

A CAIP-19 becomes a path. : and / become directory separators, so eip155:1/erc20:0xdac1… is /caip/eip155/1/erc20/0xdac1….json. A % in a reference becomes ~, because a literal % is decoded by the server before the file is ever looked up.

Read this before you trust a link

Every DTI↔CoinGecko link carries a status. They are not equally reliable and the difference is measured, not asserted:

StatusWho decidedMeasured accuracy
exactDerived from the contract address in the DTIF registry recordground truth
acceptedA human, in a reviewed pull request—
proposedA deterministic rule: exact name, optionally corroborated by ticker88.0% (name+symbol)
43.6% (name alone)
inferredA language model, with its reasoning published on the record80.8%

Those percentages come from grading the name-based tiers against the address-derived ones. If a wrong link would cost you something — a tax filing, a regulatory report — filter to exact and accepted.

Almost every error is the same error: linking a bridged or pegged deployment to the canonical asset it wraps. Two DTI records both named “USD Coin” with ticker USDC turn out to be bridged-usdc on Bitgert and celer-bridged-usdc-astar on Astar. Neither is Circle’s USDC, and no amount of name-matching could have told them apart.

A worked example: two assets called “Wrapped Ether”

Try wrapped-ether in the resolver. It returns an asset on Ethereum Classic, which looks like a bug. It is not, and the reason is worth understanding before you rely on any name.

The contract at 0x1953cab0… on Ethereum Classic reports:

name()   = "Wrapped Ether"
symbol() = "WETC"

It is WETH9 copy-deployed to another chain. The WETH9 source hardcodes name = "Wrapped Ether", and whoever deployed it changed only the symbol — so a contract that wraps ETC truthfully calls itself “Wrapped Ether”. DTIF records the name(). CoinGecko displays “Wrapped ETC” from the symbol but derives its id from the name, giving the thoroughly misleading wrapped-ether. Every one of them is reporting the contract accurately.

Two different DTI records are both named “Wrapped Ether”. One resolves to wrapped-ether on Ethereum Classic, the other to weth on Ethereum. The only thing that separates them is the contract address — which is precisely why exact links exist and why the proposed tier scores 43.6% on names alone.

Which of these 60 is the real one?

Ask for /symbol/usdc.json and you get 60 assets. Every asset carries a family saying whether it is the thing others are named after, a wrapper of something else, or neither — and groups are ordered so the head comes first.

FamilyMeansTest
canonicalOther assets are named after this onea non-derivative id that at least one other id embeds, or a second-registry attestation
derivativeIts own name says it wraps somethingbridged, wrapped, peg, wormhole, portal, staked… at a token boundary
standaloneNeither — not part of a wrapper familyeverything else

This is not a quality score, and it is built so it cannot become one. standalone is the normal state of most legitimate assets, including every new one — it does not mean “suspicious”. The buckets describe naming structure, which is observable. They say nothing about whether an asset is good, safe or real, and this project does not rate assets.

You can check it yourself. Every input is a field already in /far.json.gz — no curated list, no market data, no external feed. Recompute it from the published file and compare; the rule is about ten lines, in src/lib/family.js. Because it adds no new input, it also cannot weaken the Merkle root.

What it will not do: 86% of assets have neither citations nor a second-registry attestation, so for most of the registry this says standalone and nothing more. It finds the head of a family. It does not rank the long tail, and nothing in this data could.

Verifying what you fetched

curl -s https://0xcounting.github.io/FAR/cg/tether.json | shasum -a 256
# compare against the entry for cg/tether.json in /manifest.json

The manifest also carries a Merkle root over every (path, hash) pair, so a single file can be proven to belong to a published release without downloading the rest — an inclusion proof is about 17 hashes. Builds are deterministic: same inputs, same root.

Using it in code

const BASE = 'https://0xcounting.github.io/FAR';

// by name — returns a GROUP, because names are not unique
const r = await fetch(`${BASE}/name/${slug}.json`);
if (r.status === 404) return null;            // no asset by that name
const { assets } = await r.json();

// by CAIP-19 — ":" and "/" become path separators, "%" becomes "~"
const path = caip19.replace(/:/g, '/').replace(/%/g, '~');
const one = await fetch(`${BASE}/caip/${path}.json`);
